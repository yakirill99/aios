Команда big-data-fish. Тег репозитория: `submission-v1`.

**Заявленный ЧДД: 1 153,675 млн руб** (см. `npv_claimed.txt`).
Расписание учитывает обязательные остановки скважин 26 и 30 из
документа ограничений: без них прогон даёт 1 165,899, ремонты стоят
12,2 млн.
**Расписание: `wells_schedule.inc`** — управляющие воздействия
с 01.01.2014 по 01.12.2015, девять воздействий.

Архив данных: <https://disk.yandex.ru/d/fDUvbF-NcpWExA> — опорные
прогоны, матрица влияния, кэш ответов модели, рабочая дека. Код в
репозитории, данные в архиве.

Пошаговая установка с нуля, включая Docker и типичные ошибки, — в
`docs/INSTALL.md`. Здесь только суть.

Ожидаемый вывод: `ЧДД = 1,165.899 млн руб`, две строки по годам,

## 3. Полное воспроизведение: расписание с нуля

Нужны Docker и образ с OPM Flow.

```bash
cd ~/aios
mv ~/model ~/aios/model                     # рабочая дека из архива
docker build -t aios/opm:2026.04 -f scripts/Dockerfile scripts/
export AIOS_ROOT=$PWD DATA_ROOT=$HOME/aios-data

cd scripts
./run_schedule.sh --inc ../submission/wells_schedule.inc
./validate.sh $DATA_ROOT/runs/sched --since 2014-01-01
```

`run_schedule.sh` собирает деку с нашим расписанием, считает её и
прогоняет результат через расчёт ЧДД; в конце сам сверяет полученное
число с `npv_claimed.txt`. Один прогон — около полутора минут.

`validate.sh` проверяет физику отдельно по всему горизонту и по
управляющему окну: предел по жидкости 500 м³/сут, забойное не ниже 50
бар у добывающих и не выше 300 у нагнетательных, компенсация закачки.
На нашем расписании нарушений нет: компенсация 1,014 по всему горизонту
и 0,982 на управляющем окне при рамке 0,80–1,20.

## 4. Воспроизведение самой оптимизации

Полный перебор, без обращений к языковой модели — так получено сданное
расписание:

```bash
python3 rolling_horizon.py run --llm off --candidates 34 \
    --workdir $DATA_ROOT/check_full34
```

Восемь шагов по три месяца, на каждом до 34 кандидатов, каждый —
полный прогон симулятора. Около двух часов на шести потоках.

Тот же цикл с агентным слоем и без сети, на кэше ответов из
репозитория. Нужны два условия, иначе цикл честно предупредит и уйдёт
на правила, дав другое число:

```bash
pip install --break-system-packages pydantic     # без него agents.py не импортируется
export AIOS_LLM_MODEL=qwen3:14b                  # имя модели входит в ключ кэша

cp -r ~/aios/cache/llm $DATA_ROOT/llm_cache
python3 rolling_horizon.py run --llm replay --candidates 8 \
    --workdir $DATA_ROOT/check_replay
```

В шапке прогона должно быть «агентный слой: режим replay, модель
qwen3:14b». Если видите «промах кэша в режиме replay» — задано другое
имя модели: кэш собран именно на `qwen3:14b`.

Ожидаемый результат — **1 152,837 млн**, ровно то же число, что дал
живой прогон с моделью (`data/abl_live8/result.json` в архиве), при
нуле сетевых вызовов. Это наше доказательство воспроизводимости
агентной части. В итоговой строке прогона смотрите на «вызовов: 0,
из кэша: 24, откатов на правила: 0».

Без агентного слоя тот же цикл при том же бюджете кандидатов даёт
1 160,700 (`abl_off8`). Правила при лимите 8 обходят модель на 7,9 млн —
мы это знаем и не скрываем: ценность агентного слоя здесь в
интерпретируемости и воспроизводимости, а не в приросте.

## 5. Как устроено решение

Скользящий горизонт с триггерами. На каждом шаге снимается состояние
фонда, правила решают, есть ли повод вмешиваться, код генерирует набор
кандидатов, каждый считается полным прогоном, лучший принимается.
Глубина прогноза — весь остаток окна, поэтому кандидат оценивается по
конечному ЧДД, а не по промежуточной метрике.

Агентный слой — три роли: аналитик пишет сводку и на расчёт не влияет,
стратег сокращает список кандидатов до бюджета прогонов, критик
объясняет выбор и проверяет гипотезы. Текст критика проходит две
проверки перед записью: из него вычищаются числа, которых не было в
расчёте, и отбрасывается объяснение, приписывающее решению действия,
которых в нём нет (например, закрытие скважины, когда никто не
закрывался). В таком случае в журнал идёт формулировка, построенная
правилами, а факт отбраковки — в `llm_trace.jsonl`. **Агент не называет чисел.**
Кандидатов генерирует код из состояния скважин, модель возвращает
только теги; тег вне входного набора отбрасывается валидацией и
попадает в `llm_trace.jsonl` как отброшенный. Это проверяемое свойство,
а не обещание в промпте.

Режимов три: `off` — только правила, `live` — вызовы модели, `replay` —
кэш без сети. Режим `off` работает всегда и даёт полный результат сам
по себе. Измеренные числа всех режимов лежат в архиве:

| Прогон | Режим | Кандидатов | ЧДД, млн |
|---|---|---|---|
| `full34` | правила | 34 | 1 165,899 |
| `full34` + ремонты | правила | 34 | **1 153,675** — сдано |
| `abl_off8` | правила | 8 | 1 160,700 |
| `abl_live8` | модель | 8 | 1 152,837 |
| `abl_replay8` | кэш, без сети | 8 | 1 152,837 |
| `kam_hard8` | правила + запреты гидродинамика | 8 | 1 051,988 |

Экономический паспорт фонда (`well_passport.md`) — 49 карточек с
рекомендациями. Пороги вынесены в `configs/passport_rules.yaml` и
задаются гидродинамиком, чисел в коде нет.

## 6. Веб-интерфейс

Требуется Docker с плагином Compose. Интернет нужен только на сборку
образа; после неё интерфейс работает автономно — библиотека графиков
лежит в репозитории, внешних ссылок в нём нет.

**Данные распаковывайте ДО первого запуска**, иначе Docker создаст
каталог `~/aios-data` под пользователем root и распаковка в него
упрётся в права.

```bash
cd ~/aios
cp .env.example .env
./scripts/dashboard_preflight.sh --fix
docker compose up --build -d
```

| Адрес | Что там |
|---|---|
| <http://localhost:8000> | сводка: ЧДД против планки, фонд, агенты |
| <http://localhost:8000/dashboard.html> | журнал прогона по шагам |
| <http://localhost:8000/docs> | интерактивная документация API |

Переходы между экранами — в шапке, работают в обе стороны.

**Главный экран открывается в упрощённом режиме, часть карточек
скрыта.** Переключатель «простой / продвинутый» — в левом верхнем
углу. Продвинутый показывает гидродинамическую модель, управляющие
воздействия, содержимое `wells_schedule.inc`, параметры оптимизации и
лог.

Порт 8000 занят? Поменяйте `PORT` в `.env` и повторите
`docker compose up -d`.

### Источник данных виден на экране

Без результатов прогона интерфейс показывает эталонный набор. Источник
показан бейджем в шапке и продублирован в заголовке ответа
`X-Data-Source`: `live` — результаты прогона, `demo` — эталон, `mixed` —
часть разделов из прогона, часть эталонные. При наведении на бейдж
видна разбивка по разделам.

Сделано намеренно: эталонные данные не должны выглядеть как результат
расчёта.

Чтобы увидеть наш прогон, а не эталон:

```bash
cd ~/aios
PYTHONPATH=src python3 -m aios.dashboard.collect
curl -sD- localhost:8000/api/state -o /dev/null | grep -i x-data-source
```

Ожидается `live`. Сборщик читает `~/aios-data/rolling/journal.json` и
пишет рядом `state.json`. Ему нужен только python3 версии 3.10 и выше;
сторонних пакетов он не требует.

Проверка живости: `curl -s localhost:8000/health`.

### Запуск прогонов из интерфейса

Кнопка «Запустить прогон» открывает меню с выбором месторождения,
пресета и параметров. Дашборд при этом **сам симулятор не запускает**:
он кладёт задание в очередь, а забирает его отдельный процесс-воркер,
который нужно запустить вручную:

```bash
./scripts/dashboard_worker.sh
```

Пока воркер не запущен, задание лежит в очереди, и интерфейс прямо об
этом пишет.

Такое разделение выбрано осознанно: в образе дашборда нет симулятора, а
каталог с результатами смонтирован только на чтение. Веб-часть
физически не может изменить данные расчёта.

Если интерфейс отдаётся для просмотра и запускать ничего не нужно,
поставьте в `.env` `AIOS_READONLY=1` — кнопка исчезнет, а ручки запуска
будут отвечать отказом.

### Известное ограничение

В таблице фонда на продвинутом экране заполнены только скважины,
упомянутые в расписании; дебиты остального фонда показаны прочерками.
Ограничение сборщика, на расчёт не влияет.

## 7. Что мы знаем про ограничения решения

Отбор жадный и последовательный, а не MPC: кандидат оценивается на
полном остатке горизонта, но принятое решение дальше не
пересматривается.

Компенсация закачки считается в поверхностных условиях, тогда как
промысловая практика — в пластовых. Пороги 0,80–1,20 взяты как
разумная рамка, а не из методики. На нашем расписании 0,982, и
форсирование двигает её вниз — вероятно, это и есть настоящий потолок
форсирования, а не ЭЦН.

Часть фонда не выходит на заданный режим: скважины 40 и 44 при цели
300 и 450 м³/сут достигают 61–62% — упираются в отдачу пласта. Прирост
дают, но меньше заданного. Одиннадцать добывающих стоят на
техническом минимуме забойного 50 бар и на форсирование не отвечают.

Скважина 1 работает со стопроцентной обводнённостью при нулевой нефти.
Вариант её закрытия генерируется и оценивается; ни разу не оказался
выгоднее альтернатив — отклик по деньгам нулевой.

Экономический предел обводнённости в нашей экономике — 98,5%, а не
привычные 90–95%: маржа нефти около 8 360 руб/т против 100 руб/м³ на
подъём жидкости. Поэтому главный рычаг — форсирование отбора, а не
отключение обводнённых скважин. Прогон `kam_hard8` показывает цену
противоположной стратегии: запрет форсирования при обводнённости выше
90% и при дебите жидкости от 100 м³/сут снижает результат до
1 051,988 млн.
