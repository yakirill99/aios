## 3. Полное воспроизведение: расписание с нуля

Нужны Docker и образ с OPM Flow.

```bash
cd aios
docker build -t aios/opm:2026.04 -f scripts/Dockerfile scripts/
export AIOS_ROOT=$PWD DATA_ROOT=$HOME/aios-data
mv ~/model ~/aios/model                # рабочая дека из архива

cd scripts
./run_schedule.sh --inc ../submission/wells_schedule.inc
./validate.sh $DATA_ROOT/runs/sched --since 2014-01-01
```

`run_schedule.sh` собирает деку с нашим расписанием, считает её и
прогоняет результат через расчёт ЧДД. Один прогон — около четырёх минут
на шести потоках.

`validate.sh` проверяет физику отдельно по всему горизонту и по
управляющему окну: предел по жидкости 500 м³/сут, забойное не ниже 50
бар у добывающих и не выше 300 у нагнетательных, компенсация закачки.
На нашем расписании нарушений нет, компенсация 0,948 при рамке
0,80–1,20.

## 4. Воспроизведение самой оптимизации

Полный цикл, без обращений к языковой модели:

```bash
python3 rolling_horizon.py run --llm off --candidates 34 \
    --workdir $DATA_ROOT/check_full34
```

Восемь шагов по три месяца, на каждом оценивается до 34 кандидатов
полным прогоном симулятора. Около двух часов на машине с шестью
потоками.

Тот же цикл с агентным слоем, без сети — на кэше ответов из архива:

```bash
cp -r ~/aios-data/llm_cache $DATA_ROOT/
python3 rolling_horizon.py run --llm replay --candidates 8 \
    --workdir $DATA_ROOT/check_replay
```

Режим `replay` не делает ни одного сетевого вызова и обязан дать то же
число, что живой прогон. Это и есть наше доказательство
воспроизводимости агентной части.

## 5. Как устроено решение

Скользящий горизонт с триггерами. На каждом шаге снимается состояние
фонда, правила решают, есть ли повод вмешиваться, генерируется набор
кандидатов, каждый считается полным прогоном, лучший принимается.
Глубина прогноза — весь остаток окна, поэтому каждый кандидат
оценивается по конечному ЧДД, а не по промежуточной метрике.

Агентный слой — три роли: аналитик пишет сводку и на расчёт не влияет,
стратег сокращает список кандидатов до бюджета прогонов, критик
объясняет выбор и проверяет гипотезы. **Агент не называет чисел.**
Кандидатов генерирует код из состояния скважин, модель возвращает
только теги; тег вне входного набора отбрасывается валидацией и
попадает в `llm_trace.jsonl` как отброшенный. Это проверяемое свойство,
а не обещание в промпте.

Режимов три: `off` — только правила, `live` — вызовы модели, `replay` —
кэш без сети. Режим `off` работает всегда и даёт полный результат сам
по себе.

Экономический паспорт фонда (`well_passport.md`) — 49 карточек с
рекомендациями. Пороги вынесены в `configs/passport_rules.yaml` и
задаются гидродинамиком, в коде чисел нет.

## 6. Веб-интерфейс

Требуется Docker с плагином Compose. Других зависимостей нет.

```bash
cp .env.example .env
docker compose up --build
```

Интерфейс открывается на <http://localhost:8000>, журнал прогона — на
<http://localhost:8000/dashboard.html>, документация API — на
<http://localhost:8000/docs>.

Главный экран открывается в упрощённом режиме. Переключатель
«простой / продвинутый» в левом верхнем углу раскрывает
гидродинамическую модель, управляющие воздействия, содержимое
`wells_schedule.inc`, параметры оптимизации и лог.

Если рядом нет результатов прогона, интерфейс показывает эталонный
набор данных. Источник виден в заголовке ответа `X-Data-Source`:
`live` — результаты прогона, `demo` — эталонный набор, `mixed` — часть
разделов из прогона, часть эталонные. Сделано намеренно, чтобы
эталонные данные нельзя было принять за результат расчёта.

Чтобы увидеть наш прогон, а не эталон, распакуйте архив данных и
соберите сводку:

```bash
PYTHONPATH=src python3 -m aios.dashboard.collect
```

Сборщик читает `~/aios-data/rolling/journal.json` и пишет рядом
`state.json`; зависимостей у него нет, только стандартная библиотека.
После этого `/api/state` отвечает `live`.

Проверка работоспособности: `curl -s localhost:8000/health`.

Кнопка запуска прогона из интерфейса намеренно не работает в
контейнере: образ дашборда не содержит симулятора, а каталог с
прогонами смонтирован только на чтение.

## 7. Что мы знаем про ограничения решения

Отбор жадный и последовательный, а не MPC: на каждом шаге кандидат
оценивается на полном остатке горизонта, но принятое решение дальше не
пересматривается.

Компенсация закачки считается в поверхностных условиях, тогда как
промысловая практика — в пластовых. Пороги 0,80–1,20 взяты как разумная
рамка, а не из методики.

Часть фонда не выходит на заданный режим: скважины 40 и 44 при цели 300
и 450 м³/сут достигают 61–62% — упираются в отдачу пласта. Прирост дают,
но меньше заданного.

Скважина 1 работает со стопроцентной обводнённостью при нулевой нефти.
Вариант её закрытия генерируется и оценивается на каждом шаге; ни разу
не оказался выгоднее альтернатив.

Экономический предел обводнённости в нашей экономике — 98,5%, а не
привычные 90–95%: маржа нефти около 8 360 руб/т против 100 руб/м³ на
подъём жидкости. Поэтому главный рычаг — форсирование отбора, а не
отключение обводнённых скважин.
