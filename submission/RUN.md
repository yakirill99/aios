# Как воспроизвести результат

Пакет сдачи, трек 1, хакатон AIOS. Команда big-data-fish.

---

## Что здесь лежит

| Файл | Что это |
|---|---|
| `wells_schedule.inc` | расписание управляющих воздействий — то, что оценивается |
| `npv_claimed.txt` | заявляемое значение ЧДД, млн руб |
| `RUN.md` | этот файл |

Полный код — в корне репозитория. Данные прогонов в него не входят: они
воспроизводятся командами ниже.

---

## Заявляемое значение

```
ЧДД = см. npv_claimed.txt, млн руб
период: 01.01.2014 → 01.12.2015, 23 управляющих месяца
```

Расчёт выполнен **кодом организаторов** (`CHDD_PYTHON`,
`compute_calculation`). Своей реализации формулы ЧДД в проекте нет: две
реализации дали бы два числа, а контрольный пересчёт один.

Допущения расчёта на управляющем периоде:

```python
SUBMISSION_ASSUMPTIONS = {}      # scripts/rolling_horizon.py
```

Флаг `chargeInitialPump` **выключен**. На полной истории он нужен — там
это реальный ввод фонда, — но на управляющем окне первая строка каждой
скважины приходится на начало периода, и эталон начислил бы первичную
установку насоса всем добывающим.

```bash
cd scripts

```

Ожидается «контур готов к работе», ноль провалов.

## Воспроизведение заявленного числа

Один прогон, около двух минут. Дека собирается с нуля из выданной
организаторами модели и нашего расписания:

```bash
cd scripts
./run_schedule.sh --inc ../submission/wells_schedule.inc
```

Скрипт собирает деку, прогоняет симулятор, строит CSV, считает ЧДД
эталонным кодом и сам сверяет результат с `npv_claimed.txt`. В конце
печатается либо «ТЕСТ НА КРУГ ПРОЙДЕН», либо расхождение и код ошибки.

## Полный цикл оптимизации

Около двух часов, 208 прогонов симулятора:

```bash
cd scripts
./prepare_baseline.sh 2014-01-01 2015      # планка, режимы заморожены
python3 -u rolling_horizon.py run          # цикл
```

Умолчания соответствуют конфигурации, которой получен результат: шаг
3 месяца, уровни `0.7 / 1.25 / 1.75 / 2.25 / 3.0`, до 25 кандидатов на
шаг. Запуск без аргументов воспроизводит заявленное расписание.

## Агентный слой

Три режима, задаются флагом `--llm`:

| Режим | Что делает |
|---|---|
| `off` | языковая модель не используется, решения принимают правила |
| `live` | реальные вызовы модели, ответы копятся в кэш |
| `replay` | только кэш, ноль обращений к модели и к сети |

**Для воспроизведения используйте `replay`** — кэш ответов приложен в
`~/aios-data/llm_cache` (см. `docs/DATA_MANIFEST.md`). Ни сети, ни
запущенной модели не требуется:

```bash
python3 -u rolling_horizon.py run --llm replay
```

Режим `off` обязан работать всегда. Это и страховка демонстрации, и
доказательство того, что расчётные числа приходят из симулятора и
эталонного расчёта, а не из генерации текста: агент возвращает теги
кандидатов, сгенерированных кодом, и тег вне входного набора
отбрасывается валидацией.

## Проверка физической корректности

```bash
cd scripts
./validate.sh ~/aios-data/rolling/runs/FINAL
```

Печатает две сводки: по всей деке и отдельно по 23 управляющим месяцам.
Проверяется десять условий: дебит жидкости не выше 500 м³/сут, забойное
добывающих не ниже 50 бар, нагнетательных не выше 300, обводнённость в
[0, 1], накопленные не убывают, дебиты не отрицательны, нет NaN,
жидкость равна сумме нефти и воды, компенсация закачки в допуске,
групповые ограничения по фонду.

## Внешние ограничения

Квоты по фонду, лимиты закачки и ремонты скважин задаются в
`configs/constraints.yaml` либо отдельным файлом:

```bash
python3 constraints.py --external файл_ограничений.txt   # что распознано
python3 -u rolling_horizon.py run --external файл_ограничений.txt
./validate.sh ПРОГОН --external файл_ограничений.txt
```

Парсер терпим к формату: понимает таблицы, пары «ключ: значение» и
связный текст, даты в трёх видах. Всё нераспознанное печатается списком.

## Единицы измерения

OPM Flow не поддерживает `WOMT` и `WOMR` — это ключевые слова
tNavigator. Масса считается из объёма по плотностям из секции `DENSITY`
деки:

```
нефть    WOPT × 0,832
жидкость WOPT × 0,832 + WWPT × 1,0128
```

Плотности читаются из деки, а не заданы константой: на другом
месторождении они будут своими.

Метка даты в расчётном CSV — **дата точки сводки**, а не месяц добычи.
Разность в точке 01.02.2014 физически относится к январю, но помечается
февралём, как в эталонной таблице. Физических месяцев добычи 23: январь
2014 — ноябрь 2015, то есть 12 месяцев 2014 года и 11 месяцев 2015-го;
при разметке по точке сводки строки распределяются как 11 и 12. На
объёмы это не влияет, только на год дисконтирования.

## Если что-то не сходится

| Симптом | Причина |
|---|---|
| ЧДД около 922 млн вместо ожидаемого | включён `chargeInitialPump` на управляющем окне |
| Период начинается с 2007-04 | старая разметка дат |
| Жидкость около 7 735 вместо 7 531 тыс. т | подаётся объём вместо массы |
| Расчёт до 2022 года | дека не обрезана горизонтом; используйте `run_schedule.sh --inc` |
| `Segmentation fault` в мосте | рядом с `.SMSPEC` нет `.UNSMRY` |

Подробнее — в `docs/PIPELINE_CHECK.md`.
