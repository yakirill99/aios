# Дашборд: что можно делать и как проверить

Чек-лист для быстрой проверки на баги. Каждый пункт — что нажать и что
должно произойти. Если поведение расходится с описанным, это баг.

---

## 0. Перед проверкой

```bash
cd ~/aios
./scripts/dashboard_preflight.sh --fix    # каталоги и права
docker compose up --build
```

`mkdir -p` тут не помогает: если Docker уже создал каталог от root, на
существующем каталоге эта команда молча ничего не делает. Нужна смена
владельца — её и делает `--fix`.

В ответе `health` смотрите два поля:

- `queue_writable: true` — иначе запуск прогонов работать не будет
- `live_run` — есть ли результаты прогона рядом

Открывать: <http://localhost:8000>

---

## 1. Шапка — есть на обеих страницах

| Элемент | Где | Что должно быть |
|---|---|---|
| «Сводка» / «Журнал прогона» | слева | текущая подсвечена, обе ведут друг к другу |
| бейдж связи | справа | только на сводке; «Данные с сервера» зелёным |
| источник данных | справа | «Данные прогона» / «Эталонный набор» / «Частично эталон» |
| прогресс | справа | появляется только когда прогон идёт |
| «Запустить прогон» | справа | скрыта при `AIOS_READONLY=1` |

**Проверить:** перейти на журнал и обратно. Раньше обратной ссылки не
было — это чинилось, проверьте отдельно.

**Проверить:** навести на бейдж источника. При «Частично эталон» в
подсказке должна быть разбивка по разделам: `config: прогон`,
`wells: эталон` и так далее.

---

## 2. Сводка (`/`)

**Переключатель простой / продвинутый.** Простой прячет пять блоков:
гидродинамику, ограничения, управляющие воздействия,
`wells_schedule.inc`, параметры и лог. Выбор запоминается между
открытиями страницы.

**Кнопки-мокапы.** «Запустить оптимизацию», «Сброс», «+10 млн»,
«Случайно», «Переключить добывающую», «Сменить» у LLM — это остатки
прототипа, они рисуют выдуманные цифры.

Ожидаемое поведение: **при эталонных данных они видны и работают, при
данных прогона исчезают.** Если на реальном прогоне вы их видите —
баг. Если видите на эталоне — так задумано, это демонстрация.

**Таблица скважин.** Фильтры «Все / Добывающие / Нагнетательные»
работают всегда. Дебит и обводнённость на реальном прогоне будут
нулями — это известная незавершённость, а не баг.

---

## 3. Журнал прогона (`/dashboard.html`)

График NPV, таблица скважин, статус агентов, история действий, сырой
JSON. Данные берутся из `/api/journal`.

**Статус агентов — главное, что стоит проверить.** Карточки теперь
показывают правду:

| Прогон шёл с | Что в карточках |
|---|---|
| `--llm off` | «Не задействован», пояснение про правила |
| `--llm live/replay`, но агент не вызывался | «Не задействован», пояснение |
| `--llm live`, агент работал | «Активен», число шагов с агентом |

Если прогон был на правилах, а карточки бодро горят зелёным — баг.

## 4. Меню запуска

Кнопка «Запустить прогон» в шапке.

**Форма:**

- месторождение — из `configs/decks.yaml`, неготовые серые и не выбираются
- режим запуска — четыре пресета
- параметры: начало горизонта, число шагов, шаг управления, кандидатов,
  параллельность
- режим LLM; поле «Профиль модели» появляется **только** при «Живой вызов»

**Пресеты:**

| Пресет | Что | Время |
|---|---|---|
| Проигрывание записи | симулятор не запускается | мгновенно |
| Проверка контура | 1 шаг, 5 кандидатов | минуты |
| Короткий прогон | 2 шага, 20 кандидатов | десятки минут |
| Полный горизонт | 8 шагов, агентный слой | часы |

При выборе любого пресета кроме проигрывания появляется предупреждение
про время. Если его нет — баг.

**Проверка валидации.** Введите в «Шагов горизонта» 999 и поставьте в
очередь. Должна появиться красная плашка «Шагов горизонта: не больше
40, получено 999». Если вместо этого написано «не удалось связаться с
сервером» — баг, текст ошибки теряется.

**Проверка занятости.** Поставьте два задания подряд. Второе должно
получить отказ с номером текущего прогона.

**Отмена.** Кнопка в карточке задания. Статус переходит в «Отменён».
Идущий симулятор при этом досчитывает текущий шаг — мгновенной
остановки нет.

## 5. Прогресс прогона

Ради этого и делалась очередь: пока идёт расчёт, в шапке видно
`Прогон: шаг 3 из 8` с полосой. Обновляется каждые 3 секунды, виден на
обеих страницах, окно запуска держать открытым не нужно.

Прогресс берётся не из оценки, а из факта: цикл дописывает
`journal.json` после каждого шага, воркер считает записи.

Когда прогон заканчивается, дашборд сам подтягивает свежие данные —
перезагружать страницу не надо.

**Как проверить без долгого расчёта:** пресет «Проверка контура» — один
шаг, минуты вместо часов.

## 6. Запуск прогона целиком

**Дашборд симулятор не запускает.** Он только кладёт задание в очередь.
Забирает его воркер — отдельный процесс там, где стоит OPM. Пока воркер
не запущен, задание будет лежать в статусе «В очереди» сколько угодно.

Второй терминал, держать открытым:

```bash
cd ~/aios
./scripts/dashboard_worker.sh
```

Интерфейс теперь про это говорит: если задание в очереди, а воркера нет,
в шапке появляется «Воркер не запущен», а в окне запуска — команда для
его старта. Проверить отдельно:

```bash
curl -s localhost:8000/health | grep -o '"worker_alive":[^,]*'
```

Сначала посмотрите, что он соберёт, не запуская:

```bash
PYTHONPATH=src python3 -m aios.dashboard.worker --dry-run
```

Должна получиться команда вида:

```
python3 ~/aios/scripts/rolling_horizon.py run \
  --base ~/aios/model/Model_Y_opm --workdir ~/aios-data/rolling/<run_id> \
  --cut 2014-01-01 --end 2014-04-01 --step 3 \
  --candidates 5 --parallel 6 --llm off
```

Все флаги сверены с парсером `rolling_horizon.py`. Число шагов из формы
превращается в `--end`, потому что цикл задаёт горизонт датами.

## 7. Смена месторождения

Реестр — `configs/decks.yaml`. Дашборд разрешает прогон только по id
оттуда; произвольный путь с фронта не принимается, загрузки деки через
веб нет.

Проверить на публичной деке:

```bash
./scripts/fetch_public_deck.sh spe9     # маленькая, минуты
./scripts/fetch_public_deck.sh norne    # реальное месторождение
```

Дальше по шагам:

1. проверить, что OPM её читает
2. посчитать планку: `./scripts/prepare_baseline.sh`
3. описать ограничения в `configs/constraints.spe9.yaml`
4. снять `ready: false` в реестре

До четвёртого шага дека в меню серая и не выбирается — это защита от
прогона по несчитанной планке, а не баг.

---

## 8. Известные незавершённости

Не тратьте время на их поиск, они уже известны:

- дебит и обводнённость скважин на реальном прогоне нулевые — нужен
  разбор выхода `summary_to_csv.py` в `collect.py`
- отмена не убивает симулятор мгновенно
- прогоны пишутся каждый в свой `rolling/<run_id>/`, но `collect`
  собирает данные только для последнего
- профили LLM в `run_presets.yaml` прописаны наугад: проверьте, что
  адрес и имя модели совпадают с тем, что реально поднято

## 9. Что делать, если сломалось

```bash
curl -s localhost:8000/health              # очередь, пути, есть ли прогон
curl -s localhost:8000/api/meta            # режим, число дек и пресетов
docker compose logs dashboard | tail -40   # ошибки сервера
cat ~/aios-data/rolling/<run_id>/run.log   # что сказал сам цикл
ls -la ~/aios-data/queue/                  # файлы заданий
```

Частая поломка: `queue_writable: false`. Значит каталога
`~/aios-data/queue` не было на хосте, Docker создал его от root, а
контейнер работает под `appuser`.

```bash
docker compose down
mkdir -p ~/aios-data/queue && sudo chown -R "$USER" ~/aios-data
docker compose up
```
