# Архитектура системы · AIOS трек 1

Версия 1.0, 28.08.2026. Ответственный за документ: Кирилл.

Документ отвечает на четыре вопроса: из каких частей состоит система, как
эти части разговаривают, почему они разделены именно так, и что сломается,
если конкретная часть не будет готова.

**Чем это отличается от `REPO_STRUCTURE.md`.** Тот документ описывает
раскладку файлов на диске — где что лежит и что попадает в git. Это не
архитектура, а инвентарь. Архитектура говорит о **границах
ответственности и контрактах между ними**: почему расчёт денег живёт в
одном месте, почему агентный слой не может испортить число, что
происходит при отказе каждого компонента. Из архитектуры следует
структура репозитория, но не наоборот.

---

## 1. Контекст

```
                    ┌──────────────────────────────┐
   методика ЧДД ───►│                              │
   дека Model_Y ───►│      СИСТЕМА (наша зона)     │───► wells_schedule.inc
   нормативы    ───►│                              │───► заявленный ЧДД
                    └──────────────┬───────────────┘───► объяснения решений
                                   │
                        ┌──────────┴──────────┐
                        ▼                     ▼
                   OPM Flow              CHDD_PYTHON
                   (симулятор)        (эталон организаторов)
                   внешняя система      внешняя система
```

Обе внешние системы **неизменяемы**. Симулятор — источник физики,
эталонный расчёт — источник денег. Всё, что делает наша система,
сводится к одному: подобрать вход для симулятора так, чтобы выход
эталонного расчёта был максимальным.

## 2. Три архитектурных решения, определяющих всё остальное

### AD-1. Расчёт денег — библиотека организаторов, не наш код

**Решение.** Своей реализации формулы ЧДД в системе нет. `npv_official.py`
вызывает `compute_calculation()` из `vendor/chdd/chdd_model.py` напрямую.

**Почему.** Организаторы делают один контрольный пересчёт. Две реализации
формулы дают два числа, а расхождение сверх пары процентов —
дисквалификация. Единственный способ гарантировать совпадение — считать
тем же кодом.

**Следствие.** Расчёт денег — **библиотека**, а не сервис. Её импортируют
и оркестратор, и рабочий процесс симуляции; физически она существует в
обоих. Требование «единственный источник правды» решается тем, что это
библиотека: две копии кода дают два разных ЧДД, две копии одной
библиотеки — одно и то же.

**Проверка.** `verify_reference.sh`: +0,16% на периоде 2007–2015, сверено
счётчиками событий.

### AD-2. Числа приходят из физики, LLM — из семантики

**Решение.** Агент не называет величин, попадающих в расчёт. Кандидатов
генерирует код из состояния скважин; агент возвращает **теги**
кандидатов, а не значения дебитов.

**Почему.** Иначе FR-7.2 держится на честном слове промпта, и на защите
придётся доказывать, что число в расписании не выдумано моделью. При
выбранной схеме доказательство занимает одну строку: тег, которого не было
во входном наборе, отбрасывается валидацией.

**Следствие.** Ценность агента измерима одним числом — разницей ЧДД между
режимами `off` и `live` на одинаковой конфигурации. Режим `off` не
заглушка, а рабочий вариант поставки.

### AD-3. Дискретная сетка вместо непрерывной оптимизации

**Решение.** Управление задаётся множителями текущего режима из конечного
набора `{0.7, 1.25, 1.75, 2.25, 3.0}`, а не непрерывной величиной.

**Почему.** Гистерезис ЭЦН: насос меняется вверх сразу, вниз только при
падении больше 100 м³/сут ниже границы. Значит ЧДД зависит от истории
режимов, а целевая функция разрывна. Градиентные и эволюционные методы на
разрывной функции с дорогим вычислением (2–4 минуты на точку) работают
плохо.

**Следствие.** Оптимизация сводится к перебору на сетке, и главным
ресурсом становится **бюджет прогонов**. Отсюда триггеры, отсюда же роль
агента — сузить перебор.

## 3. Компоненты

Компонент — это то, что можно увидеть в `docker ps`, поставить через
`pip install`, найти через `ls` или пингануть. «Диагностика» и «генерация
гипотез» — не компоненты, а функции внутри них.

| Тип | Компонент | Что внутри | Интерфейс |
|---|---|---|---|
| Процесс | **Orchestrator** | `rolling_horizon.py`: цикл MPC, триггеры, журнал | CLI |
| Процесс | **Simulation Worker** | `run_flow` в контейнере, пул потоков | вызов из оркестратора |
| Процесс | **LLM runtime** | Ollama, модель 14B Q6 | HTTP `localhost:11434` |
| Библиотека | **NPV Library** | `npv_official.py` → `vendor/chdd` | `import` |
| Библиотека | **Data Bridge** | `summary_to_csv.py`: UNSMRY → 14 колонок | `import` / CLI в контейнере |
| Библиотека | **Schedule Builder** | `schedule_builder.py`: словарь действий, рендер `.inc` | `import` |
| Библиотека | **State Reader** | `read_state.py`: сводки → состояние фонда | CLI в контейнере |
| Библиотека | **Interference** | `probe_wells.py`, `analyze_probes.sh` → матрица влияния | CSV |
| Библиотека | **Agent Layer** | `agents.py`, `llm_client.py`: три роли, схемы, кэш | `import` |
| Библиотека | **Validator** | `validate_output.py`: физика + компенсация | CLI в контейнере |
| Хранилище | **Run Storage** | `~/aios-data/runs`, `rolling` | файловая система |
| Хранилище | **LLM Cache** | `~/aios-data/llm_cache`, ключ = хеш(модель, T, промпт, схема) | файловая система |
| Хранилище | **Journal** | `journal.json`, `llm_trace.jsonl` | JSON / JSONL |
| Внешняя | **OPM Flow** | — | запуск бинаря в контейнере |
| Внешняя | **CHDD_PYTHON** | — | `import` |
| Интерфейс | **Dashboard** | `ui/`: ЧДД, Ганта, карта, объяснения | браузер |

**Чего в системе нет намеренно.** Суррогатной модели — трек 1 позволяет
гонять физику напрямую. Очереди задач — на одной машине её заменяет
`ThreadPoolExecutor`. Базы данных — журнал в JSON переживает перезапуск и
читается глазами. Каждый отсутствующий компонент это сэкономленные дни,
которые ушли в интерпретируемость и дашборд.

## 4. Поток данных: один шаг цикла

```
                    ┌─────────────────────────────────────────┐
                    │  состояние фонда x_t                    │
                    │  (дебиты, обводнённость, BHP, темп)     │
                    └────────────────┬────────────────────────┘
                                     │
                          ┌──────────▼──────────┐
                          │  diagnose()         │  правила, пороги из Config
                          └──────────┬──────────┘
                                     │
                          ┌──────────▼──────────┐
                          │  check_triggers()   │──нет──► наблюдение, шаг++
                          └──────────┬──────────┘
                                     │ да
              ┌──────────────────────▼──────────────────────┐
              │  АНАЛИТИК (LLM)   что происходит на объекте │ ─► только в отчёт
              └──────────────────────┬──────────────────────┘
                                     │
                          ┌──────────▼──────────┐
                          │  pick_targets()     │  4 доб. + 2 нагн.
                          └──────────┬──────────┘
                                     │
                          ┌──────────▼──────────┐
                          │  make_candidates()  │  N кандидатов, ЧИСЛА ЗДЕСЬ
                          └──────────┬──────────┘
                                     │  N штук
              ┌──────────────────────▼──────────────────────┐
              │  СТРАТЕГ (LLM)    отбор K из N по ТЕГАМ     │ ─► влияет на ЧДД
              └──────────────────────┬──────────────────────┘
                                     │  K штук
                    ┌────────────────▼────────────────┐
                    │  Simulation Worker × parallel   │
                    │  дека → OPM Flow → UNSMRY       │
                    └────────────────┬────────────────┘
                                     │
                    ┌────────────────▼────────────────┐
                    │  Data Bridge → NPV Library      │  ЧИСЛА ЗДЕСЬ
                    └────────────────┬────────────────┘
                                     │  {тег: ЧДД}
                          ┌──────────▼──────────┐
                          │  argmax, порог 2 млн│
                          └──────────┬──────────┘
                                     │
              ┌──────────────────────▼──────────────────────┐
              │  КРИТИК (LLM)     почему выиграл этот       │ ─► только в отчёт
              └──────────────────────┬──────────────────────┘
                                     │
                    ┌────────────────▼────────────────┐
                    │  зачётный прогон → x_{t+1}      │
                    │  journal.json, llm_trace.jsonl  │
                    └─────────────────────────────────┘
```

Обратите внимание на два блока, помеченных «ЧИСЛА ЗДЕСЬ». Оба —
детерминированный код. Между ними LLM работает только с тегами.

## 5. Контракты между компонентами

Контракты замораживаются первыми: пока граница зафиксирована, два
человека пишут по разные стороны, не мешая друг другу.

| Граница | Контракт | Формат |
|---|---|---|
| Orchestrator → Simulation Worker | каталог деки + каталог выхода | файловая система, `flow.log` с `End of simulation` |
| Simulation Worker → Data Bridge | `*.SMSPEC` + `*.UNSMRY` | бинарный формат resdata |
| Data Bridge → NPV Library | `chdd_input.csv`, 14 колонок | `DATA, well, WLPT, WLPR, WOMT, WOMR, WWIR, WWIT, THP, BHP, WEFF, *_Diff` |
| NPV Library → Orchestrator | `NPVResult` | `.npv` (млн руб), `.years[]`, `.diagnostics` |
| Orchestrator → Schedule Builder | `list[Action]` | `date, well, control, value, reason` |
| Schedule Builder → дека | `wells_schedule.inc` | секция `SCHEDULE` в синтаксисе OPM |
| Orchestrator ↔ Agent Layer | теги кандидатов | `list[tuple[str, list[Action]]]` внутрь, `list[Pick]` наружу |
| Agent Layer → LLM runtime | JSON Schema в `format` | HTTP `/api/chat`, `temperature=0`, `seed=42` |
| Всё → Dashboard | `journal.json`, `llm_trace.jsonl`, `result.json` | JSON / JSONL |

**Ключевая деталь контракта с агентом.** Наружу агент отдаёт только те
теги, которые получил на вход. Валидация в `rank_candidates` отбрасывает
всё остальное и логирует количество отброшенных. Это и есть механическая
гарантия FR-7.2, а не обещание в промпте.

## 6. Режимы работы

| Режим | LLM | Кэш | Когда |
|---|---|---|---|
| `off` | не используется | — | разработка расчётной части, страховка демо, доказательство корректности |
| `live` | реальные вызовы | пишется | рабочие прогоны, накопление кэша |
| `replay` | не используется | только чтение | поставка организаторам: воспроизведение без сети и без ollama |

Система обязана давать результат во всех трёх. Деградация до правил
происходит при: режиме `off`, промахе кэша в `replay`, недоступности
ollama, ошибке разбора схемы, невалидных тегах в ответе. Каждый случай
логируется.

## 7. Отказоустойчивость

| Компонент | Отказ | Поведение системы |
|---|---|---|
| LLM runtime | недоступен | деградация до правил, цикл продолжается |
| Agent Layer | вернул мусор | теги отбрасываются, берётся правиловый порядок |
| Simulation Worker | прогон упал | кандидат исключается из сравнения |
| Simulation Worker | все прогоны шага упали | шаг пропускается, пишется в журнал |
| NPV Library | исключение | кандидат исключается, `check_before_compute` отбраковывает заранее |
| Orchestrator | прерван | `journal.json` позволяет `resume` с последнего шага |
| Диск | меньше 30 ГБ | `disk_guard` останавливает работу и пишет отчёт |
| Два запуска | одновременно | lock-файлы в `rolling/`, `verify_reference.sh` |

Единственный отказ, который система не переживает, — недоступность
`vendor/chdd`. Это осознанно: без эталона считать деньги нечем, и
подменять его своей формулой хуже, чем остановиться.

## 8. Трассировка: требование → компонент

| Требование | Кто закрывает | Что сломается без него |
|---|---|---|
| ЧДД совпадает с пересчётом | NPV Library, Data Bridge | дисквалификация |
| Расписание читается моделью | Schedule Builder | дисквалификация |
| Ограничения на всём периоде | Validator | дисквалификация |
| Компенсация закачки | Validator, Schedule Builder | дисквалификация |
| Максимизация ЧДД | Orchestrator, Interference | низкое место в ранжировании |
| Интерпретируемость (FR-7.2) | Agent Layer, Journal | потеря критерия оценки |
| Визуализация | Dashboard | потеря критерия оценки |
| Воспроизводимость | LLM Cache, `journal.json`, тег `submission-v1` | проблемы в финале |
| Масштабируемость | конфигурация вместо констант | вопросы жюри |

Обратная проверка — есть ли компоненты, не закрывающие ни одного
требования. На сегодня таких нет: `probe_wells` закрывает
«максимизацию», `read_state` — её же, `cleanup` — эксплуатационное
требование по месту.

## 9. Масштабируемость

Жюри спросит, что произойдёт при переходе на другой участок. Ответ
разложен по осям:

**Другая дека.** Даты не зашиты: `CUT_DATE` и `END_DATE` в
`lib_common.sh`, список скважин читается из `SCHEDULE`, типы
определяются по наличию векторов закачки. Правки под OPM
задокументированы в `CHANGES_FOR_OPM.md` и воспроизводятся.

**Больше скважин.** Матрица влияния строится за `2n+1` прогонов и
масштабируется линейно. Отбор целей ограничен `n_prod + n_inj`, а не
полным фондом, поэтому число кандидатов от размера фонда не зависит.

**Дороже прогон.** Здесь появляется суррогат — тот самый компонент,
которого сейчас нет намеренно. Точка встраивания уже есть:
`Runner.simulate` и `Runner.npv` — единственные места, где система
обращается к физике. Замена одного класса.

**Длиннее горизонт.** Динамический фильтр связей (`лаг + месяц ≤
горизонт`) параметризован горизонтом. На длинном окне закачка начнёт
выигрывать сама, без правок кода.

## Приложение. Как читать этот документ на защите

Семь минут защиты не вмещают всю схему. Показывать стоит один слайд —
раздел 4, поток данных одного шага, с подсветкой двух блоков «ЧИСЛА
ЗДЕСЬ». Он отвечает сразу на три вопроса жюри: как система понимает
объект, откуда берётся число, и что именно делает LLM. Остальные разделы
— для вопросов.
