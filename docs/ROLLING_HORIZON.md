# Скользящий горизонт

`rolling_horizon.py` · `read_state.py`

Цикл управления с обратной связью: на каждом шаге читаем состояние
объекта, решаем что делать, применяем, идём дальше.

---

## Отличие от статического перебора

Статический перебор ищет **конфигурацию**: какие режимы выставить один
раз и держать весь горизонт. Скользящий горизонт ищет **расписание**:
последовательность воздействий во времени, реагирующую на изменение
состояния.

Скважина обводнилась к середине периода — статика продолжает её
форсировать, цикл замечает и меняет режим.

**Это не MPC.** Окно не скользит: при глубине прогноза, равной всему
остатку горизонта, каждый кандидат оценивается на полном остатке, а
принятое решение дальше не пересматривается. Получается жадный
последовательный отбор с обратной связью по состоянию. Называем вещи
своими именами: от MPC здесь взята схема «состояние → решение →
применение», но не пересмотр плана.

---

## Алгоритм шага

```
1. состояние x_t из последнего зачётного прогона
2. диагностика: кто обводнился, у кого запас, где закачка вхолостую
3. проверка триггеров: нужно ли вообще вмешиваться
4. отбор скважин для рассмотрения
5. генерация кандидатов из словаря действий
6. оценка каждого прогоном на окне [cut, t + lookahead]
7. выбор argmax ЧДД, если выигрыш выше порога
8. зачётный прогон победителя → состояние для шага t+1
```

Целевая функция на окне:

```
max  Σ  CF(x_k, u_k) / (1 + r)^(k/12),   k = t .. t+H
```

**Применяется только выбранное действие**, состояние для следующего шага
берётся из зачётного прогона победителя. Две причины: от факта считать
надёжнее, чем от прогноза; плюс обратная связь — если обводнённость
выросла быстрее ожидаемого, следующее решение это учтёт.

---

## Почему не жадный выбор

Жадный алгоритм максимизирует поток текущего шага. При лаге отклика
4–6 месяцев эффект от закачки придёт позже, а платить надо сейчас —
жадный её никогда не назначит.

Глубина прогноза `lookahead` должна покрывать лаг. На горизонте 23 месяца
она равна всему остатку: смотреть дальше конца бессмысленно, окно всё
равно обрезается.

---

## Триггеры

Вмешиваться на каждом шаге бессмысленно и дорого. Три обоснования:

| | |
|---|---|
| **Экономика** | переключение стоит ~1 млн, смена ЭЦН 2,35–9,85 млн |
| **Физика** | медиана лага 4–6 мес, раньше результата не видно |
| **Вычисления** | меньше шагов — меньше прогонов |

Между срабатываниями система **наблюдает**: снимает состояние, считает
производные, пишет трейс — но воздействий не назначает. В журнале такие
шаги помечаются `observe`.

Расписание при этом остаётся помесячным: `DATES` идёт каждый месяц,
просто в большинстве месяцев пусто. Частота решений и детализация файла —
разные вещи.

### Пять условий

| Триггер | Условие | Обоснование |
|---|---|---|
| **Прорыв воды** | обводнённость > 97,5% | приближение к экономическому пределу 98,5% |
| **Падение продуктивности** | темп > 8% за шаг | потеря добычи требует реакции |
| **Убыточность** | вклад в поток < 0 | скважина тратит больше, чем приносит |
| **Закачка вхолостую** | нет полезных связей в окне | затраты без отдачи |
| **Первый шаг** | всегда | точка передачи управления |

Достаточно одного сработавшего.

### Динамика по горизонту

Триггер закачки **не статический**. Он учитывает, сколько месяцев
осталось:

```python
useful_degree(well, months_left) = |{ lag : lag <= months_left }|
```

Нагнетательная, чьи связи не успеют проявиться, считается бесполезной —
даже если у неё много связей вообще. Связь с лагом 10 месяцев работает на
5-м месяце и бесполезна на 18-м.

При `months_left < 6` цикл печатает предупреждение: только форсирование
отбора, закачка не успеет отработать.

Это прямое следствие позиции организаторов: «эффект отложенных решений не
доживает до оценки за пределами горизонта, терминальная стоимость запасов
в критерий не входит, оптимизируйте строго внутри окна».

### Порог выигрыша

```
min_gain_mln = 2.0
```

Если лучший кандидат даёт меньше 2 млн — не переключаемся. Само
переключение стоит около миллиона, плюс риск смены ЭЦН.

## Диагностика

Считается на каждом шаге независимо от триггеров:

| Признак | Порог | Комментарий |
|---|---|---|
| `water_breakthrough` | обводнённость > 97,5% | не 90%, как в литературе |
| `unprofitable` | маржа < 0 руб/сут | `8360·q_oil·0,832 − 100·q_liq` |
| `headroom` | запас > 50% до 500 м³/сут | есть куда форсировать |
| `declining` | темп падения > 8% | по нефти за 6 шагов назад |
| `idle` | скважина закрыта | |

## Отбор скважин

Из 49 скважин на каждом шаге рассматриваются 4 добывающих и 2
нагнетательных — иначе кандидатов будет слишком много.

**Добывающие** ранжируются по:

```
score = headroom + 0.1 · useful_degree(well, months_left)
      + 0.3 (если падает дебит)
      + 0.5 (если убыточна)
```

**Нагнетательные** — по связности из матрицы:

```
score = |useful_degree − 2| · 0.2 + 0.3
```

Интересны и сильно связанные (есть что усилить), и вовсе несвязанные
(есть что придушить). При `useful_degree = 0` и `months_left < 10`
скважина исключается совсем.

**Минимальный интервал** между воздействиями на одной скважине — 9
месяцев. Медиана лага 4–6, дёргать чаще бессмысленно.

## Кандидаты

Из словаря допустимых действий, ничего изобретённого.

**Одиночные:** каждая отобранная скважина × каждый уровень.
Уровни: `0.7, 1.25, 1.75, 2.25, 3.0`. Сетка дискретная, потому что
гистерезис ЭЦН делает целевую функцию разрывной: насос меняется вверх
сразу, вниз только при падении больше 100 м³/сут ниже границы.

**Пакетные** — добавлены после того, как выяснилось, что цикл по одному
воздействию за шаг проигрывает статике из-за дисконта:

| Тег | Что делает |
|---|---|
| `PACK_prod_x1p5` | форсировать до четырёх добывающих сразу |
| `PACK_inj_redistribute` | нарастить одну нагнетательную, придушить другую |
| `PACK_full` | форсирование + перераспределение закачки |

Всего до 34 кандидатов на шаг. Цена сужения перебора измерена: 34
варианта стоят 127 минут, сужение до 25 теряет 3,8 млн (0,33%), до 8 —
5,2 млн (0,45%) и экономит две трети времени.

## Что даёт на практике

Горизонт 23 месяца, шаг 3 месяца, 8 шагов:

| Шаг | Осталось | Выбрано | Выигрыш |
|---|---|---|---|
| 1 | 23 мес | `PACK_prod_x1p5` — скв. 14, 27, 31, 40 | +99,2 |
| 2 | 20 мес | `44_x3` | +8,9 |
| 3 | 17 мес | `43_x3` | +25,6 |
| 4 | 14 мес | `40_x3` | +3,5 |
| 5 | 11 мес | `24_x2p25` | +7,6 |
| 6 | 8 мес | `4_x3` | +2,1 |
| 7–8 | ≤ 5 мес | `noop` | 0 |

```
планка:      1 018,986 млн руб
расписание:  1 165,899 млн руб  (без ремонтов; сдано 1 153,675)
дельта:      +146,9 млн (+14,42%)
воздействий: 9
время:       127 минут
```

Четыре наблюдения:

**Первый шаг даёт 68% всего прироста** — пакетное форсирование четырёх
скважин сразу. Дальше отдача быстро падает.

**Отдача убывает.** Раннее воздействие ценнее позднего: работает дольше
и меньше дисконтируется.

**Последние два шага — бездействие.** На остатке в 5 и 2 месяца ни один
вариант не окупает переключения: смена режима стоит замены ЭЦН, а эффект
не успевает накопиться. Триггер «осталось N месяцев» это предсказывал,
расчёт подтвердил числом.

**Ни одна скважина не закрыта.** При экономическом пределе обводнённости
98,5% закрывать невыгодно даже скважину 1 со стопроцентной
обводнённостью: её вариант закрытия генерируется и оценивается, но
отклик по деньгам нулевой.

Три прогона с разным бюджетом кандидатов (34, 25, 8) дали одинаковые
решения на первых четырёх шагах до десятой доли — независимая проверка
воспроизводимости, которую не пришлось ставить отдельно.

## Бюджет прогонов

```
N = T × (K + 1) + 2
```

где `T` — шагов, `K` — кандидатов, плюс опорный и финальный прогоны.

| Шаг | Шагов | K | Прогонов | Время |
|---|---|---|---|---|
| месяц | 23 | 20 | 485 | ~4 ч |
| квартал | 8 | 20 | 170 | **~80 мин** |
| полгода | 4 | 20 | 86 | ~42 мин |

Квартальный шаг — разумный компромисс: чаще медианы лага, но не
избыточно.

## Возобновляемость

Состояние пишется в `journal.json` после каждого шага:

```bash
python3 rolling_horizon.py run       # с нуля
python3 rolling_horizon.py resume    # продолжить прерванный
```

Lock-файл `.lock` в рабочем каталоге не даёт запустить второй экземпляр —
два процесса пишут в один каталог и затирают результаты друг друга.

---

## Команды

```bash
cd ~/aios/scripts

python3 rolling_horizon.py plan --step 3     # план без прогонов

nohup python3 -u rolling_horizon.py run --step 3 --candidates 20 \
    > ~/aios-data/logs/rolling.log 2>&1 &
tail -f ~/aios-data/logs/rolling.log
```

Флаг `-u` обязателен: без него вывод буферизуется и лог остаётся пустым
часами.

### Параметры

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--cut` | 2014-01-01 | начало управления |
| `--end` | 2015-12-01 | конец горизонта |
| `--step` | 3 | шаг управления, месяцев |
| `--lookahead` | 23 | глубина прогноза |
| `--candidates` | 25 | кандидатов на шаг (сдано на 34) |
| `--levels` | 0.7,1.25,1.75,2.25,3.0 | множители режима |
| `--llm` | off | `off` / `live` / `replay` |
| `--constraints` | configs/constraints.yaml | лимиты, квоты, ремонты |
| `--events` | — | файл недоступности скважин |
| `--policy` | — | запреты из паспорта: закрытие, запрет форсирования |
| `--no-triggers` | — | вмешиваться на каждом шаге |
| `--min-gain` | 2.0 | порог выигрыша, млн |
| `--parallel` | 6 | параллельных прогонов |

## Ограничения

**Жадность по шагам.** Выбирается лучшее действие на текущем шаге с
учётом окна, но не оптимальная последовательность целиком. Принятое
решение не пересматривается.

**Ограниченный набор кандидатов.** 34 на шаг из пространства, которое при
шести скважинах и пяти уровнях составляет 5⁶ = 15 625 комбинаций. Цена
этого ограничения измерена, см. раздел о кандидатах.

**Часть фонда не отвечает.** Одиннадцать добывающих стоят на техминимуме
забойного 50 бар; скважины 40 и 44 при цели 300 и 450 м³/сут выходят
на 61–62%. Расширять сетку вверх для них бессмысленно.

**Матрица снята в одной точке.** Связи меняются по мере выработки, а цикл
использует их фиксированными на всём горизонте.
