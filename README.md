# AIOS · Трек 1 — мультиагентная система управления фондом скважин

Система подбирает расписание управляющих воздействий на 49 скважинах,
максимизируя ЧДД на управляющем горизонте при соблюдении технологических
ограничений.

| | |
|---|---|
| Модель | Model_Y: 49×47×141 = 324 723 ячейки, 49 скважин (33 доб. + 16 нагн.), 3 разлома |
| Управляющий горизонт | **01.01.2014 → 01.12.2015, 23 месяца** (12 мес 2014 + 11 мес 2015) |
| Планка (режимы заморожены) | **1 018,986 млн руб** |
| Лучший результат цикла | **1 165,899 млн, +146,9 (+14,42%)** |
| Сверка расчёта денег с эталоном | **+0,16%** на периоде 2007–2015 |
| Ранжирование | по абсолютному подтверждённому ЧДД, не по приросту |

Декабрь 2015 в расчёт не входит: помесячная разность накопленных величин
для него не образуется — нужна точка 01.01.2016, а её в деке нет.

## Быстрый старт

```bash
cd ~/aios/scripts

./setup_dirs.sh                       # структура каталогов, проверка окружения
./smoke_test.sh                       # проверка контура на эталонной SPE1
./verify_reference.sh                 # сверка ЧДД с эталоном организаторов
./prepare_baseline.sh 2014-01-01 2015 # планка: должно выйти 1 018,986 млн

python3 -u rolling_horizon.py run     # цикл оптимизации (~100 мин)
./validate.sh ~/aios-data/rolling/runs/FINAL   # физкорректность перед сдачей
```

Сданный результат получен полным перебором: шаг 3 мес, уровни
`0.7,1.25,1.75,2.25,3.0`, **34 кандидата** на шаг, горизонт прогноза
23 мес, режим `off`. Воспроизведение — около двух часов:

```bash
python3 rolling_horizon.py run --llm off --candidates 34 \
    --workdir ~/aios-data/check_full34
```

Установка с нуля, включая Docker, архив данных и языковую модель, —
`docs/INSTALL.md`. Инструкция для организаторов — `submission/RUN.md`.

Требуется Docker с образом `aios/opm:2026.04` — сборка в `INSTALL.md`.

## Скрипты

Все пути и даты заданы в `lib_common.sh` — единственном месте, где они
есть. Переопределяются переменными окружения:
`MODEL_DIR=/путь ./benchmark.sh`.

### Основа

| Файл | Назначение |
|---|---|
| `lib_common.sh` | пути, `CUT_DATE`, `END_DATE`, стражи диска и памяти, `run_flow`, `run_py` |
| `setup_dirs.sh` | создание структуры, проверка прав и окружения |
| `smoke_test.sh` | проверка контура на SPE1 |
| `benchmark.sh` | замер: время прогона, оптимум параллельности, место |

### Расчёт денег

| Файл | Назначение |
|---|---|
| `npv_official.py` | ★ обёртка над эталоном организаторов, своей арифметики нет |
| `summary_to_csv.py` | мост UNSMRY → 14 колонок для расчёта ЧДД |
| `verify_reference.sh` | сверка с эталоном 5 326,5 млн + проверка раскладки планки |

`verify_reference.sh` ничего не пересобирает без явного флага. Планку он
только проверяет: 23 месяца, 2014 — 12, 2015 — 11. Пересборка по
`--with-baseline`, поверх существующей — только `--with-baseline --force`
с подтверждением.

### Подготовка сценариев

| Файл | Назначение |
|---|---|
| `prepare_history.sh` | прогон истории → снимок пласта + датасет |
| `prepare_baseline.sh` | режимы заморожены → планка ЧДД |
| `schedule_builder.py` | ★ генератор `wells_schedule.inc` |
| `run_schedule.sh` | прогон расписания + сравнение с планкой |

### Матрица влияния

| Файл | Назначение |
|---|---|
| `probe_wells.py` | генерация возмущений и разбор откликов |
| `run_probes.sh` | прогон 99 вариантов (~46 мин) |
| `analyze_probes.sh` | сборка матрицы |

Меняем режим одной скважины на ±30%, смотрим отклик остальных. Это
управляемый эксперимент — даёт причинность, а не корреляцию. Результат:
615 связей, 272 уникальные пары из 2 401 (разреженность 11%), медиана
лага по нефти 4–6 месяцев, антисимметрия 94%.

### Оптимизация

| Файл | Назначение |
|---|---|
| `rolling_horizon.py` | ★ цикл скользящего горизонта с триггерами |
| `read_state.py` | чтение состояния фонда (внутри контейнера) |
| `candidates.py` | генератор кандидатов, дискретная сетка |
| `run_candidates.sh` | пакетный прогон кандидатов |

### Проверка и обслуживание

| Файл | Назначение |
|---|---|
| `validate_output.py` | ★ физкорректность + компенсация закачки |
| `validate.sh` | обёртка; по умолчанию считает и управляющий период |
| `cleanup.sh`, `cleanup_stale.sh` | уборка результатов |
| `git_prepare.sh` | подготовка репозитория к коммиту |

### Агентный слой

| Файл | Назначение |
|---|---|
| `llm_client.py` | клиент LLM: режимы off / live / replay, structured output |
| `agents.py` | три роли: аналитик, стратег, критик |

```bash
python3 agents.py test                       # проверка ролей, без ollama
python3 -u rolling_horizon.py run --llm live # цикл с агентом
```

Режим `off` обязан работать всегда: система деградирует до правил, и это
доказывает, что числа не приходят из генерации текста.

## Что важно знать

### Расчёт ЧДД — только эталонный

`vendor/chdd/chdd_model.py` — код организаторов, единственный источник
правды по деньгам. `npv_official.py` — тонкая обёртка. Вторая реализация
формулы означала бы расхождение при контрольном пересчёте, а попытка
одна.

Сверка на периоде 2007–2015: расхождение **+0,16%**, разложено до
рубля. Подтверждено счётчиками событий, а не только суммой: смены ЭЦН
57 против 58, остановки/пуски 48 против 48, переводы 15 против 15.

Допущения зафиксированы одной константой `SUBMISSION_ASSUMPTIONS` в
`rolling_horizon.py`, и на управляющем окне она **пуста**:
`chargeInitialPump` не начисляется. На полной истории 2007–2008 флаг,
наоборот, нужен — там это реальный ввод фонда. Цена ошибки измерена:
с флагом на управляющем окне планка выходит 922,7 вместо 1 018,986,
то есть 96,3 млн.

### Даты

```
01.05.2007   старт модели
01.01.2014   точка передачи управления  (CUT_DATE)
01.12.2015   последний расчётный шаг    (END_DATE)
```

Метка даты в CSV — **дата точки сводки, а не месяц добычи**, как в
эталонной таблице организаторов. Разность в точке 01.02.2014 физически
относится к январю, но помечается февралём. Физических месяцев добычи
23; при разметке по точке сводки строки распределяются как 11 в 2014 и
12 в 2015. На объёмы это не влияет, только на год дисконтирования —
ошибка стоила 0,76% ЧДД.

Даты в скрипты не зашиты: `--cut` и `--end` задаются аргументами, число
шагов и глубина прогноза считаются из них. Проверить на произвольном
горизонте: `rolling_horizon.py plan --cut 2012-01-01 --end 2018-12-01`.

### Единицы

OPM Flow **не поддерживает** `WOMT`/`WOMR` — это ключевые слова
tNavigator. Масса нефти считается из объёма: `WOPT × 0,832` т/м³ —
плотность первого PVT-региона из секции `DENSITY`, не среднее по двум.
Разница в 0,001 т/м³ стоит 7,6 млн ЧДД. Жидкость у организаторов в
тоннах, а `WLPT` — объём: без пересчёта `WOPT × 0,832 + WWPT × 1,0128`
расхождение по жидкости 2,7%.
`THP`, `BHP`, `WEFF` в формулы ЧДД не входят, но колонки обязаны
присутствовать.

### Экономика определяет стратегию

| Параметр | Значение | Следствие |
|---|---|---|
| Маржа нефти | ~8 360 руб/т | нефть дорогая |
| Подъём жидкости | ~100 руб/м³ | вода почти бесплатна |
| Экономический предел обводнённости | **98,5%** | не 90–95%, как в учебниках |
| Средний дебит фонда | 87 м³/сут при потолке 500 | фонд работает на 17% потолка |
| Смена ЭЦН | 2,35–9,85 млн | частые переключения невыгодны |

Отсюда два вывода, на которых стоит вся стратегия: закрывать
обводнённые скважины почти всегда убыточно, а главный рычаг —
форсирование отбора, потому что эффект приходит без лага.

### Короткий горизонт меняет стратегию

23 месяца при медиане лага отклика 4–6 месяцев по нефти. Форсирование
работает сразу, закачка успевает проявиться только в первой половине
окна. Терминальная стоимость не учитывается, поэтому матрица связей
фильтруется динамически: связь полезна, если `лаг + месяц вмешательства
≤ 23`.

### Гистерезис ЭЦН

Насос меняется вверх сразу при выходе за диапазон, вниз — только при
падении больше чем на 100 м³/сут ниже нижней границы. Значит ЧДД зависит
от **истории** режимов, целевая функция разрывна, и непрерывная
оптимизация неприменима. Отсюда дискретная сетка множителей.

### Ограничения

```
дебит жидкости          ≤ 500 м³/сут   (выше расчётчик ЧДД падает)
забойное добывающих     ≥ 50 бар
забойное нагнетательных ≤ 300 бар
обводнённость           в [0, 1]
накопленные             не убывают
компенсация закачки     в [0,80; 1,20] — проверяется, порог настраивается
```

Проверяются на всём прогнозном периоде и отдельно на управляющем окне.
Физически некорректные значения в выходных файлах расцениваются как баг
и грозят дисквалификацией.

**Ограничения валидационного кейса** (документ организаторов от
11.09.2026) лежат в `configs/constraints_case.yaml` и
`configs/events_case.txt`:

```
суммарная добыча жидкости  ≤ 4000 м³/сут
суммарная закачка          ≤ 4000 м³/сут
программа ремонтов         8 скважин, остановки обязательные
```

На сданном расписании пик по фонду 3 392 м³/сут жидкости и 3 556
закачки — в лимиты укладываемся. В управляющее окно попадают ремонты
скважин 26 (01.10.2014–01.02.2015) и 30 (01.05.2015–01.09.2015); они
внесены в расписание как `WELOPEN SHUT` и `OPEN`. Цикл, запущенный с
`--constraints` и `--events`, дополнительно вычёркивает кандидатов на
скважины в ремонте и печатает это в журнал.

### Место и память

Прогон без снимков — 25 МБ, из них 22 МБ статика (`EGRID`, `INIT`);
со снимками (`RPTRST`) до 1,3 ГБ. Все скрипты отключают `RPTRST` для
пробных прогонов. Страж останавливает работу при 30 ГБ свободного места.

Внутри WSL `df` показывает размер виртуального диска (~1 ТБ), но VHDX
лежит на диске C: свободное место = минимум из ext4 и `/mnt/c`.
`MemAvailable` в WSL не отражает физически свободную память Windows,
поэтому параллельность ограничивается по ядрам: 8 процессов × 2 потока =
145 прогонов/час.

### Правки деки

Дека сделана в tNavigator и без правок не читается OPM Flow. Убраны блок
`#if 0...#endif`, `IMPLICIT`, CRLF→LF; из SUMMARY убраны
`WOMT`/`WOMR`/`WTHP`/`WEFF`/трассерные, добавлены `WOPT`/`WOPR`. Все
изменения — в `model/CHANGES_FOR_OPM.md`. Каждая строка там —
потенциальный источник расхождения при пересчёте.

**Готово.** Контейнер OPM Flow 2026.04. Пайплайн расчёта денег сверен с
эталоном. Планка пересчитана. Матрица влияния построена: 615 связей,
медиана лага 4 мес. Цикл скользящего горизонта работает и возобновляем.
Валидатор физкорректности прогнан на финальном результате без нарушений.
Агентный слой с тремя ролями, три режима, абляция всех трёх замерена.
Экономический паспорт фонда с порогами в YAML. Механизм внешних
ограничений: групповые квоты, недоступность скважин, парсер событий.
Дашборд. Тест на круг одной командой. Полная проверка развёртывания на
чистой машине.

**Измеренные результаты** (одна планка 1 018,986, одна конфигурация):

| Прогон | Режим | Кандидатов | ЧДД, млн |
|---|---|---|---|
| `full34` | правила | 34 | **1 165,899** — сдаём |
| `rolling_v4` | правила | 25 | 1 162,145 |
| `abl_off8` | правила | 8 | 1 160,700 |
| `abl_live8` | модель `qwen3:14b` | 8 | 1 152,837 |
| `abl_replay8` | кэш, без сети | 8 | 1 152,837 |

Совпадение `live` и `replay` до третьего знака при нуле сетевых вызовов
— доказательство воспроизводимости агентной части. Агент при равном
бюджете кандидатов уступает правилам 7,9 млн; мы это знаем и не
скрываем: ценность агентного слоя в интерпретируемости и
воспроизводимости, а не в приросте.

**Известные ограничения.** Отбор жадный и последовательный, а не MPC.
Компенсация закачки считается в поверхностных условиях, пороги
0,80–1,20 — разумная рамка, а не методика. Одиннадцать добывающих стоят
на техминимуме забойного 50 бар и на форсирование не отвечают. В таблице
фонда на дашборде заполнены только скважины из расписания.

**Открытые вопросы к организаторам:** налог на имущество — текст
методики относит к OPEX, в формуле его нет; стоимость ЭЦН-50 =
0,90397 млн выглядит опечаткой.

## Сдача

В `submission/`:

- `wells_schedule.inc` — расписание, читается моделью без правок
- `npv_claimed.txt` — заявленное абсолютное значение ЧДД
- `RUN.md` — как воспроизвести
- исходный код, документация, `docker compose up`

Заявляемое число берётся **только** из финального прогона, посчитанного
с `SUBMISSION_ASSUMPTIONS`, и подтверждается тестом на круг: расписание
собирается с нуля и считается заново, полученное число сверяется с
заявленным. Перед сдачей — тег `submission-v1`, чтобы знать, какой код
породил сданное число.

Проверка одной командой:

```bash
./make_submission.sh                  # перенос, тест на круг, валидатор
./release.sh                          # кэш модели, слияние dev в main, тег
./make_data_archive.sh                # архив данных для Яндекс.Диска
```

Один контрольный расчёт на стороне организаторов. Расхождение сверх пары
процентов — дисквалификация, повторов нет.
